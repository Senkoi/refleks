# 数据准入、校准与验证准备

目的：在确定各场景家族算法前，把需要证明的关系、样本单位和验证方法固定下来。此处不选择回归/排序模型，也不制定特征权重。

## 一、样本单位

基础样本不是“某图名字”或“某 benchmark 的 Intermediate”，而是：

`场景文件 hash + 活动配置/阶段 + 条件约束 + 目标表现定义 + 标签证据快照`

按用途分三张表：

1. **机制样本**：文件、引用图、地图、武器、移动、计分和结束条件，以及特征提取状态。
2. **表现样本**：同一文件/版本上的目标分数、分数单位、benchmark 门槛版本、该门槛的原生段位。
3. **玩家适配样本**：玩家近期的多次可比表现、日期、设置、练习量与状态；其个人适配不能反过来冒充客观场景难度。

相同场景有多个目标分数时，各行共享机制特征但表现要求不同。不能以不同门槛复制同一张图、再声称获得多个独立文件样本。

## 二、标签证据等级

| 证据 | 本轮如何使用 | 禁止的推断 |
|---|---|---|
| 官方当前 benchmark 门槛 | 原生表现标签 | 同名段位跨体系等价 |
| 作者预期 VT 范围 | 弱区间与采样优先级 | 把整个难度组压成一个段位或文件难度 |
| 同类、同一批玩家、相近时间的成绩 | 待独立采集的跨体系校准证据 | 直接比较不同图原始分数 |
| 公开社区配对报告 | 寻找候选配对、审查差异 | 未拿到原始数据就采纳其 confidence 或回归式 |
| 多人社区体感 | 补充异常解释、提出复查候选 | 把帖子数量当独立样本量 |
| 单人体验、名称 easy/hard、playlist 标题 | 线索 | 自动生成监督标签 |

不同来源出现冲突时保留原始记录与范围，禁止平均成一个“可靠难度”。

## 三、跨体系玩家数据采集合同

公开 leaderboard 接口已实际成功返回成绩，以及 `attributes` 中的 FOV、cm360、epoch、scenarioVersion、clientBuildVersion、hash、pauseCount、pauseDuration、sensRandomizer、modelOverrides 等键。字段的存在不保证每条成绩都有值，也不保证这些 hash/version 的含义等于 .sce SHA-256。

后续采集要记录：

- 精确排行榜 ID、抓取时间、页码、页大小、返回总量、实际数量、请求失败/限流、重复记录。
- 在匹配阶段临时使用稳定玩家标识；公开交付只保留匿名配对与汇总，不把用户名、硬件简介等无关信息写进模型。
- 成绩时间、场景版本、游戏版本、分数单位、暂停/覆盖/随机灵敏度等条件的存在率。
- 两图交集人数、两侧交集占比、各能力区间覆盖、练习次数是否可得，以及是否只能得到历史最佳成绩。

单独记录 API `counts.entries` 与 leaderboard `total`；二者未必同义，不混用计算百分位。

**首次联网只读探查不构成配对校准完成。**本轮没有抓取并独立重算 39 对完整玩家数据。后续不能只抓榜单前列后声称代表全体玩家。

`data/leaderboard-probe.json` 记录了本轮实际探查：VT Raw Control Intermediate S5（98048）与 Whisphere Viscose（184107）各取榜单前 100 条，稳定 ID 交集为 36 人。两侧这批记录均带 epoch、scenarioVersion 和 clientBuildVersion；sensRandomizer 在这批中均为空，其他条件字段也有缺失。这只证明关联路径可用，不作为相近难度结论；当前采样不具人群代表性。

玩家配对流程：

1. 文件确认是同一能力类别后再匹配玩家；跨类别高相关不足以构成等难度。
2. 检查分数单位与当前门槛，不把接口中整数缩放形式混进原始分数。
3. 同一玩家两次成绩需有相近时间和兼容条件；允许的时间窗口应先试查数据覆盖，再在验证前固定，并做窗口敏感性分析。
4. 按能力区间检查覆盖和不确定性；样本少时扩大区间或标未知。初始家族数/样本量配额不是统计显著性的保证。
5. 验证历史最佳成绩的练习量偏差。只得到 PB 时，结论只能描述 PB 人群关系，不能解释每局稳定表现或疲劳。
6. 最终交叉对齐给出区间及证据等级，保留原生段位；不生成全体系精确换算表来掩盖误差。

## 四、文件样本准入

进入算法候选训练集前，必须同时满足：

- 取得当前真实文件，字节 hash 和来源明确；文件与场景 ID 的关联经核验。
- 根到活动 bot、rotation、character、weapon、dodge、地图和相关 ability 的依赖已解决；缺少的能力不会影响该次特征时需写明理由。
- 主目标与环境辅助 bot 已区分，同时保留环境影响。
- 目标大小、距离、相对速度和地图缩放的单位经过核验。不能把裸字段当真实角度。
- 武器、计分、结束条件和动态阶段有明确处理；无效/缺省字段没有被当作真实零值。
- 标签绑定具体门槛、版本与表现目标；同类跨家族的“相近难度”有具体证据，不仅是组名相同。

当前数据中的 `calibration_eligible=false` 不得在缺少上述证据时整体改成 true。

## 五、验证划分与评价方案

- **整家族留出**：同家族所有尺寸/速度/时长变体、不同季节改名版本必须进入同一折；至少再做一版更保守的同源组留出。
- **文件去重**：完全相同 hash、仅注释/名称不同的机械等价文件不得分别充当独立训练/验证样本；机械等价判断本身留证。
- **时间隔离**：旧版数据与当前门槛不能随机打散。算法选定后使用未参与选择的新时间段或新场景做最终验证。
- **玩家隔离**：模型若使用玩家成绩作标签或特征，验证要按玩家分组，避免同一人泄漏；文件外推与玩家外推分开报告。
- **基线比较**：与名称标签、benchmark 组标签以及只用尺寸/速度的简化方法比较，说明文件分析实际增加了什么。
- **评价对象分离**：类内排序、段位区间覆盖、区间宽度、跨家族误差、unknown 比例分别报告。不能只给一个相关系数。
- **误差检查**：高低段、各家族、不同地图/计分机制分别看偏差，避免总体好看但某类失效。
- **反事实文件检查**：同一文件只改不影响玩法的标题不应改变机制特征；尺寸、速度、时长变体应被解释为哪个机制改变，而不预先强制所有变化在所有任务中同方向影响难度。

允许的误差和最终发布阈值在数据规模与标签噪声审查后、模型比较前写定。本轮不给没有数据支持的准确率承诺。

## 六、确定算法前的完成门槛

1. 本轮文档、身份清单、原生门槛、来源和格式反例已准备。
2. 待补：81 张首轮当前文件及实际运行语义核验；随后按家族覆盖扩充难度梯度。
3. 待补：至少对拟建模子类建立可信的跨家族相近表现区间；rA 没有现成 VT 换算时保留原生区间。
4. 待补：独立玩家配对或作者明确的逐场景证据，以及覆盖/偏差审查。
5. 冻结可入选样本、同源分组、验证集和误差判据后，才开始比较具体家族算法。

无法达到门槛的类别继续保留 unknown；允许先推进证据充分的子类，无需让所有类别同时上线。
